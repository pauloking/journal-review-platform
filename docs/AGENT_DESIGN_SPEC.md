# 中文科技期刊智能审校能力平台 — 智能体设计书

- **文档版本**：1.1（对应当前基线版本，演进自提交 `a09e5fd` 并完成第 2 轮安全/可靠性加固）
- **适用工程**：`journal-review-platform`
- **编写原则**：严格区分**当前版本已实现并经测试验证的能力**与**后续规模化演进规划**，不虚构未落地的线上指标或未测数据。

## 一、建设背景

### 1.1 行业与业务痛点
中文科技期刊（尤其是医学科技期刊）在初审、编辑加工与校对环节长期面临三大难题：
1. **规范标准繁杂且跨层叠加**：一篇医学稿件需同时符合国家标准（如 GB/T 15835-2011 数字用法、GB 3100~3102 量和单位、GB/T 15834-2011 标点符号、GB/T 7714-2025 参考文献）、行业规范（全国科技名词委审定医学名词、GB/T 3358 统计学符号）、期刊自身体例以及编辑经验规则，人工逐项核对耗时且易遗漏。
2. **传统纯提示词 AI 工具不可控**：将审校逻辑直接写入大模型提示词的早期应用普遍存在「黑箱运行、易漏检、幻觉引文、编造标准条款、无法精确回写 Word 原文位置、重复运行结果不一致」等工程缺陷，难以作为严肃出版生产系统长期演进。
3. **历史成果分散、缺少统一能力底座**：核查本机历史项目时发现两类成熟资产各自独立——Python 侧的 `medical-journal-copyediting-2.0.0` 沉淀了四层结构化规则与章节识别模型（25/25 用例通过），Web 侧的 `medical-journal-reviewer` 沉淀了原生 Word 批注注入防踩坑经验、综合审评报告导出、大模型 JSON 截断修复与 SQLite 统计口径（95 项测试通过），但缺乏统一的数据协议与任务编排中枢。

### 1.2 建设目标
基于上述背景，本项目确立核心建设原则：**建设可扩展的审校能力平台（Review Platform），而非一次性单点应用**。当前版本围绕首个应用领域——**医学科技期刊**，打通“DOCX 安全解析 → 规范文档装载 → Router DAG 编排 → 确定性规则与复算核验 → 受控大模型语义审校（OpenAI / Claude / 自定义兼容接口）→ 锚点与依据门禁 → 编辑裁决与原生批注导出”的完整纵向闭环。

## 三、设计框架

平台采用**协议驱动的分层解耦架构**，确保任何一层能力均可独立测试、替换与升级，各层职责与红线如下：

```
+-----------------------------------------------------------------------+
| 应用与交互层 (Application Layer)                                      |
|  · 编辑工作台 Web UI (review_platform/static/)                        |
|  · FastAPI 服务接口 (review_platform/api.py)                          |
|  · 命令行工具 CLI (python -m review_platform)                         |
+-----------------------------------------------------------------------+
                                   |
                                   v
+-----------------------------------------------------------------------+
| 核心能力编排层 (Review Platform Core Engines)                         |
|  1. Document Engine   : DOCX 安全解析 -> DocumentIR + ManuscriptProfile|
|  2. Knowledge Engine  : 结构化条款 + 9份Markdown规范文档 + 期刊配置   |
|  3. Rule Registry     : 版本化 RuleSpec 注册 + basis_id 校验 + 正反例 |
|  4. Router            : Kahn 确定性 DAG 编排（零静默遗漏、环/缺失拦截）|
|  5. Review Engine     : FactLedger抽取 + 确定性规则/复算 + AI适配器底座|
|  6. Finding Engine    : 锚点逐字核验 + 依据真实性门禁 + 稳定ID去重    |
|  7. Editorial Engine  : SQLite 裁决事件 + 原生批注DOCX + 综合报告DOCX |
|  8. Evaluation Engine : 黄金集度量 + 问题大类归并 + 编辑反馈评估队列  |
+-----------------------------------------------------------------------+
                                   |
                                   v
+-----------------------------------------------------------------------+
| 可插拔执行层 & 基础设施层                                             |
|  · 确定性引擎：regex 超时防回溯执行器 / Decimal 复算校验器            |
|  · 受控 AI 引擎：OpenAI / Claude / 自定义兼容适配器（SSRF与密钥隔离）|
|  · 安全与存储：Bearer RBAC 鉴权、SQLite (WAL)、sessionStorage 会话配置 |
+-----------------------------------------------------------------------+
```

### 核心设计约束（工程红线）
1. **逻辑不硬编码**：规则与规范条款存于结构化知识包与注册表，不写死在前端或提示词中；
2. **知识库不等同于向量库**：以精确条款编号、版本、适用章节与例外规则为核心契约；
3. **任务不静默遗漏**：`RuleRegistry` 中每条规则必在 `ExecutionPlan` 留痕（`passed / findings / skipped / failed / blocked`）；
4. **AI 不越权、不编造**：禁止自动修改科研数据，禁止引用未登记的 `basis_id`，AI 候选仅作待裁决建议且须过门禁。

## 四、技术路线

围绕「**确定性规则 + 专业计算工具 + 受控 AI 语义审校**」三轨协同路线，当前版本已落地的主体技术链路与预留扩展路线如下：

### 4.1 稿件中间表示协议（`document-ir/1.0`）
- **零清洗保真提取**：直接解析 OOXML `word/document.xml` 顶层 `<w:p>` 与 `<w:tbl>` 单元格，精确提取 `<w:t>`、`<w:tab/>`、`<w:br/>`、`<w:cr/>` 可见文本与直接 `<w:r>` 的 Unicode 码点区间（`RunSpan`），避免正误替换导致坐标错位。
- **确定性指纹与安全防线**：以 DOCX 原始字节 `SHA-256` 作为 `document_id`；强制拦截空文件、超 10 MiB 文件、ZIP 炸弹（30 MiB / 1000 成员）、XXE 外部实体（`<!DOCTYPE`/`<!ENTITY`）及未定稿 Word 修订（`<w:ins>`/`<w:del>`/`<w:moveFrom>`/`<w:moveTo>`）。
- **结构画像复用**：通过 `review_platform/adapters/legacy_structure.py` 复用 `manuscript_model.py` 实现中文医学论著章节分类与引号示例上下文区间识别；共享纯文本工具拆分至 `review_platform/document_engine/text_utils.py`，消除反向依赖。

### 4.2 文档化知识体系与规则门禁
- **规范文档与条款绑定**：将四层规范整理为 9 份结构化 Markdown 文档与 `clauses.json`，支持通过 `parse_rule_document_bytes`（`review_platform/knowledge_engine/doc_parser.py`）上传 `.md/.txt/.docx/.json` 文件自动抽取对照表格与规则条目（带解压成员与大小防炸弹校验）。
- **ReDoS 与正反例自动校验发布**：新增或修订规则保存前，静态拦截嵌套量词（含 `+`/`*`/`{m,n}`）与超长示例（500 字上限），使用带 200ms 硬超时的 `regex` 引擎执行 `validate_maintainable_rule` 验证「必命中正例 + 不误报反例」，并通过 `advanced_params` 无损保留及类型校验。

### 4.3 确定性 Router DAG 与可视化执行追踪
- **拓扑规划**：采用 Kahn 算法（字典序堆）对所有已注册规则（含 `ai_candidate`）与前置 `extract.facts` 节点进行确定性拓扑排序；检测环依赖、缺失依赖或未知禁用规则；上游节点失败时显式将下游置为 `blocked`。
- **6 阶段过程追踪**：每次运行产出 `ReviewRun.trace`（`document_parse` → `knowledge_bind` → `router_plan` → `fact_extract` → 按规范文档汇总的 `rule_execute` → `finding_gate`），并在工作台可视化呈现。

### 4.4 专业计算复算与原生 Word 批注写回
- **零浮点漂移复算**：使用 Python `Decimal` 复算 `n/N(pct%)` 与显示精度半单位/期刊容差比较，检验 P 值 `[0, 1]` 边界及独立图/表题注序列。
- **原生 OOXML 批注导出**：`review_platform/editorial_engine/word_exporter.py` 在核验原稿 `SHA-256` 一致且意见最新裁决为 `accept` 后，基于 `RunSpan` 与 `lxml` 精确拆分 `<w:r>` 注入批注，支持同段多条非重叠批注；对重叠或既有批注冲突显式跳过并通过响应头列明。另提供 `review_platform/editorial_engine/summary_exporter.py` 导出综合审评 Word 报告。

### 4.5 受控大模型语义协同路线（已实现用户可配置并行接入）
- **实时可控接入与并行执行**：`review_platform/review_engine/llm_adapter.py` 已实现 OpenAI、Claude (Anthropic) 及自定义兼容接口（DeepSeek / GLM / Qwen / Ollama / OneAPI）适配器；启用时通过 `ThreadPoolExecutor` 按激活的 AI 维度并发调用，支持关闭推理思考链（`enable_thinking: false`）与连接测试 `/llm/test`。
- **端到端安全防线与门禁**：
  1. **密钥同源隔离与会话存储**：前端将 LLM 配置与 API Key 仅存放在标签页级 `sessionStorage`（关闭即清除）；后端严格校验仅当 `endpoint` 与服务端默认地址同源时才允许回落使用环境变量 `REVIEW_LLM_API_KEY`，严禁向第三方自定义地址发送服务端密钥；
  2. **SSRF 与错误脱敏**：拒绝含 query/fragment 的 URL、禁止重定向并默认阻断所有非公网全球路由 IP（含 `localhost` / 内网 / CGNAT `100.64.0.0/10` / 云元数据 `169.254.0.0/16` 及 DNS 重绑定），私有本地模型仅限通过 `REVIEW_LLM_LOCAL_ALLOWLIST` 精确登记 `host + port + path`；上游非 2xx 错误仅摘要状态码与结构化错误码，不透传原始响应体；
  3. **真实门禁与长稿截断显式降级**：AI 候选均经 `extract_json_block` / `repair_json` 容错、动态日期防误判过滤、`Anchor` 逐字定位与 `basis_id` 校验；单次带块前缀上下文超过 24,000 字符截断时，无论是否产出 Finding 均通过独立任务元数据记录 `context_truncated_24k`、强制写入 `document.limitations` 并降级状态为 `complete_with_limitations`。

## 五、资源需求

### 5.1 当前版本基础资源需求
不启用外部大模型时，单机可完全离线低成本稳定运行：
- **计算与内存**：2 vCPU / 1–2 GB RAM（单篇万字级 DOCX 解析与全套确定性规则执行耗时在百毫秒级）。
- **运行环境**：Python 3.11+（已在 Python 3.12.13 验证），核心依赖为 `fastapi`、`uvicorn`、`pydantic`、`python-docx`、`lxml`、`regex`、`httpx`、`python-multipart`；测试依赖 `pytest`。
- **存储需求**：本地 SQLite（WAL 模式）存放运行快照、裁决历史、评估反馈与自定义规范文档；原始 DOCX 字节与 LLM API Key 均不入库存储。

### 5.2 开启 AI 审校与编辑部多用户试点新增资源需求
- **模型算力/API 配额**：支持 OpenAI / Claude / 自定义 OpenAI 兼容接口或私有化推理服务（推荐上下文 >= 32K tokens、支持关闭思考链 `enable_thinking: false` 降低超时风险）。
- **鉴权与基础设施升级**：单机试点可设置 `REVIEW_API_TOKENS` 启用 Bearer 四角色 RBAC 鉴权并在前端顶部输入会话令牌；规模化生产部署建议升级 PostgreSQL、异步任务队列、HTTPS 反向代理网关与独立脱敏策略。
- **领域与标注人力**：需要 2 名以上资深医学期刊编辑参与脱敏黄金样本双盲标注与仲裁，构建规则级精度/召回基线；涉及国家标准全文授权与医学术语库更新时需配合相应版权与专家评审资源。

## 六、预期效果

### 6.1 当前版本已可实测验证的效果
1. **自动化验证全通过**：当前工程自动化测试套件覆盖 DOCX 安全防线、精确锚点、ReDoS 静态与 `regex` 超时熔断、DAG 失败阻断、数值与题注边界例外、规则文档无损往返、Bearer RBAC、SSRF 与密钥同源隔离、长稿截断降级、原生 Word 批注写回及综合报告导出（最新实测记录见 `docs/EVALUATION.md`）。
2. **复用基线可追溯**：继承的 `medical-journal-copyediting-2.0.0` 在其 25 例基准测试中达成 `TP=20, FP=0, FN=0 (F1=1.000)`；`medical-journal-reviewer` 原有 95 项前端与导出测试全部通过。
3. **100% 确定性定位与零静默遗漏**：所有已通过门禁的 Finding 均保证原文区间逐字可验证，Router DAG 中每条规则执行或跳过状态均有明确追踪。

### 6.2 演进与试点阶段预期目标（门禁指标，待真实脱敏样本验证）
- 确定性规则定位准确率保持 **100%**；
- 核心高风险确定性规则在双编辑仲裁黄金集上实现 Precision >= 95%、Recall >= 90% 与重大退化为 0；
- 结合受控 LLM 语义审校后，进一步覆盖“摘要与结果数字一致、方法与结果指标呼应、图文表数据交叉核对”等跨位置语义审校场景，显著降低编辑初筛与格式加工机械耗时，同时保持全部裁决可审计。

## 七、可能的风险与伦理合规考虑

| 风险类别 | 具体风险描述 | 平台当前与演进防控措施 |
|---|---|---|
| **1. 科研数据篡改风险** | 审校工具或 AI 误改稿件中的样本量、P 值、效应量或实验结论，引发严重科研诚信问题 | 平台硬性规定 `DocumentIR` 只读；Word 批注导出**只写批注不改正文**；数值复算仅提示「请编辑核实原始数据」 |
| **2. AI 幻觉与伪造依据** | 后续接入大模型后可能编造不存在的国家标准条款、虚构文献或将当期投稿年份误判为“未来时间” | 强制 `basis_id` 必须存在于 `KnowledgeEngine`；未通过原文 `Anchor` 逐字核验的候选全部拦截入 `rejected_candidates`；内置运行时日期基准注入与误判过滤 |
| **3. 隐性漏检与误导性通过** | 系统因解析失败、作用域不匹配或静默跳过规则而输出虚假的“全稿无错”结论 | Router 禁止静默丢弃任务；解析限制（页眉页脚/脚注/图片/公式未纳入定位）强制写入 `limitations` 与导出报告；修订稿明确拒绝导入 |
| **4. 规则污染与误报扩散** | 未经检验的编辑反馈或临时规则直接覆盖正式规则，导致全量稿件误报激增 | 编辑裁决仅进入 `evaluation_feedback` 队列；在线新增/修改规则文档必须通过正反例自动校验门禁方可保存 |
| **5. 稿件保密、密钥与 SSRF 防护** | 未发表医学手稿含科研机密与患者信息，外发第三方模型存在保密风险，自定义接口存在密钥泄露与 SSRF 风险 | 不开启 AI 时完全本地离线运行；开启时 API Key 仅存 `sessionStorage` 且严格同源隔离，禁止透传 `REVIEW_LLM_API_KEY` 到自定义地址，并校验阻断内网与元数据 SSRF；上线公网须配合 HTTPS 与脱敏策略 |
| **6. 标准版权与责任主体** | 未经授权转载国家标准全文引发版权纠纷；编辑过度依赖自动化结果导致审稿把关失责 | 知识库当前仅存储结构化标准编号、条款摘要与核查逻辑，不非法分发标准全文；平台定位为**编辑辅助审校**，最终学术与出版裁决权及签名责任始终归属期刊编辑 |
